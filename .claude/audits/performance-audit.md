## Performance — Print3D Manager ERP

**Escopo revisado:** N+1 em Java (listagens e mappers), paginação nos endpoints REST, custo das agregações nativas do dashboard/financeiro/relatórios além do que `database-audit.md` já cobriu (índices), e frontend (TanStack Query staleTime/cache, padrões de fetch, bundle). Não repetidos os achados de índice já reportados em `.claude/audits/database-audit.md` (A1–A3, M1–M5, B1–B4).

### Achados

1. [ALTO] Relatórios PDF sem limite de período — full scan + geração síncrona em memória
   - Onde: `backend/src/main/java/com/print3dmanager/erp/report/controller/ReportController.java:46-85` (parâmetros `de`/`ate` livres) e `backend/src/main/java/com/print3dmanager/erp/report/service/ReportService.java:167-178` (`resolverPeriodo` só valida `de > ate`, sem teto de intervalo); consultas em `ReportQueryRepository.pedidosDoPeriodo`/`transacoesDoPeriodo`/`consumoPorFilamento` (sem `LIMIT`, carregam `List<Object[]>` inteira). No frontend, `frontend/src/pages/reports/ReportsPage.tsx:114-129` usa `<TextField type="date">` sem `min`/`max`, e `baixar()` (linha 87) só bloqueia `de > ate` (nenhum teto de intervalo).
   - Cenário que dispara o custo: qualquer usuário com `PODE_CONSULTAR` (ADMINISTRADOR/OPERADOR/FINANCEIRO/VISUALIZADOR) escolhe um período de vários anos (ex.: `de=2020-01-01`) em `/reports/pedidos`, `/reports/financeiro` ou `/reports/consumo-filamento` — nada no backend nem na UI impede isso.
   - Custo estimado: consulta nativa sem `LIMIT` retorna todas as linhas do período direto para uma `List<Object[]>` em memória, e o `PdfReportBuilder` monta o PDF inteiro (uma linha de tabela por registro) de forma síncrona na thread da requisição HTTP, segurando a transação `readOnly` aberta o tempo todo. Cresce linearmente com `pedidos`/`transacoes_financeiras`/`historico_impressoes` — em produção real (não TCC), um relatório "desde o início" pode travar a thread por segundos/minutos e consumir memória proporcional ao volume histórico.
   - Recomendação: (a) impor um teto de intervalo no `ReportService.resolverPeriodo` (ex.: máx. 12–24 meses, análogo ao `Math.clamp` já usado no `DashboardService`) devolvendo 400 quando excedido; (b) espelhar o teto no frontend (`min`/`max` nos `TextField type="date"` ou validação antes do `baixar()`); (c) se relatórios de intervalo maior forem necessários futuramente, considerar geração assíncrona (job + download posterior) em vez de síncrona.
   - Agente sugerido para aplicar: `backend` (teto + 400) e `frontend` (limitar o seletor de datas).

2. [MÉDIO] `topClientes` agrega histórico inteiro de `pedidos` sem janela de tempo, ao contrário das demais séries do dashboard
   - Onde: `backend/src/main/java/com/print3dmanager/erp/dashboard/repository/DashboardQueryRepository.java:100-112` (`topClientes`) — `SELECT c.id, c.nome, count(p.id), sum(p.valor_total) FROM pedidos p JOIN clientes c ... WHERE p.status <> 'CANCELADO' GROUP BY c.id, c.nome ORDER BY sum(p.valor_total) DESC ... LIMIT :limite` — sem `WHERE` de data. Chamado por `DashboardService.topClientes` (`dashboard/service/DashboardService.java:118-128`) a cada carregamento de `GET /dashboard/top-clientes`, que é disparado toda vez que `DashboardPage.tsx` monta (`frontend/src/pages/DashboardPage.tsx:201-204`, sem `staleTime` próprio — usa o default global de 30s).
   - Cenário que dispara o custo: qualquer navegação para `/dashboard` (rota inicial pós-login) após 30s da última visita.
   - Custo estimado: diferente de `pedidosPorMes`/`faturamentoPorMes`/`consumoFilamentoPorMes` (todas com `WHERE ... >= :inicio` sobre uma janela de N meses), esta faz `GROUP BY`+`ORDER BY sum(...)` sobre **todos** os pedidos não cancelados desde o início do sistema, em toda visita ao painel — o índice existente em `pedidos.cliente_id` (V6) não evita o full scan da tabela para a agregação/ordenação por soma. Tende a crescer sem limite conforme o histórico de pedidos aumenta, mesmo que o "top 5" real quase nunca mude entre execuções.
   - Recomendação: coordenar com `erp` se "top clientes" deveria ser janelado (ex.: últimos 12 meses, como as outras séries) ou é intencionalmente "all-time" — se for intencional, considerar cache de curta duração no backend (a query já é barata para volume de TCC) ou, se o volume crescer, uma tabela de rollup/materialized view.
   - Agente sugerido para aplicar: `backend` (ajuste de query) coordenado com `erp` (decisão de negócio sobre o período).

3. [BAIXO] `AtividadeRecente` busca 20 clientes ordenados por nome só para aproximar "os 3 mais recentes" no cliente
   - Onde: `frontend/src/pages/dashboard/AtividadeRecente.tsx:34-38` — `clientsApi.listar({ page: 0, size: 20, ativo: true })` com o comentário "A API só ordena por nome — os mais recentes são achados no cliente"; `frontend/src/api/clients.ts:57` hardcoda `sort: 'nome,asc'` em toda chamada (não há como o caller pedir outro sort). O componente então re-ordena os 20 resultados por `criadoEm` no cliente e corta os 3 primeiros (linhas 50-52).
   - Cenário que dispara o custo: toda visita ao dashboard busca 20 clientes (ordenados alfabeticamente) para descartar 17 e usar só 3 — e, à medida que a base de clientes crescer além de 20, os "3 mais recentes" mostrados deixam de ser necessariamente os mais recentes de fato (ficam enviesados para nomes no início do alfabeto), o que é tanto desperdício de fetch quanto um problema de correção.
   - Custo estimado: baixo em volume absoluto (paginação server-side, só 20 linhas), mas é fetch redundante recorrente (a cada carregamento do dashboard) que poderia ser 1 linha de resposta em vez de 20, e piora silenciosamente em precisão com o crescimento da tabela.
   - Recomendação: expor `sort` como parâmetro em `FiltrosClientes`/`clientsApi.listar` (o backend já aceita `Pageable` com sort arbitrário, `ClientController` usa `@PageableDefault(sort="nome")` só como default) e chamar com `sort: 'criadoEm,desc', size: 3` — resolve fetch desnecessário e a imprecisão ao mesmo tempo.
   - Agente sugerido para aplicar: `frontend`.

4. [INFORMATIVO] Busca rápida do cabeçalho amplia 3× o custo da busca textual sem índice já sinalizada por `database-audit.md` (B3)
   - Onde: `frontend/src/layout/BuscaRapida.tsx:36-50` — a cada termo estável (debounce de 400ms via `useDebounce`, `frontend/src/hooks/useDebounce.ts:4`), dispara 3 `useQuery` em paralelo (`ordersApi.listar`, `clientsApi.listar`, `filamentsApi.listar`), cada um batendo em `busca` (`LOWER(...) LIKE '%termo%'` nas respectivas Specifications) — exatamente o padrão que `database-audit.md` (B3) já identificou como não indexável por btree comum (wildcard à esquerda).
   - Cenário que dispara o custo: usuário digita no campo `Ctrl+K` do cabeçalho (visível em todas as páginas para todos os perfis internos) — cada termo estável gera 3 sequential scans concorrentes em `pedidos`/`clientes`/`filamentos`.
   - Custo estimado: o debounce de 400ms mitiga bem a frequência; não é um achado novo de causa (a causa raiz é B3, já reportado), mas é um novo ponto de amplificação — 3 tabelas escaneadas por keystroke estável em vez de 1, a partir de um widget global de alta visibilidade/uso.
   - Recomendação: nenhuma ação nova além da já recomendada em B3 (avaliar `pg_trgm`/GIN se a busca precisar escalar); mencionado aqui só para o agente `database`/`frontend` terem visibilidade de que a correção de B3 beneficia particularmente este componente.
   - Agente sugerido para aplicar: `database` (já é o dono de B3); nenhuma ação de `frontend` necessária hoje.

### Sem achados nesta área
- **N+1 em listagens paginadas**: todos os endpoints de listagem (`/clients`, `/users`, `/filaments`, `/inventory`, `/printers`, `/orders`, `/quotes`, `/prints`, `/financial/transactions`) usam `Pageable` + `JpaSpecificationExecutor`; onde a entidade tem relação relevante exibida na listagem, há `@EntityGraph` explícito confirmado em código: `OrderRepository` (cliente na listagem resumida; cliente+usuário+itens+filamento no detalhe), `QuoteRepository` (cliente/usuário/impressora/filamento/pedido), `PrintHistoryRepository` (impressora/filamento/itemPedido/itemPedido.pedido/usuário), `FinancialTransactionRepository` (pedido/cliente). `Client`, `User`, `Printer`, `Filament`, `InventoryItem` não têm coleções mapeadas nos DTOs de listagem (`PrinterResponse`/`PrinterMapper` conferidos — sem relação `@OneToMany`/config carregada em loop), então não há N+1 a proteger ali.
- **Ausência de paginação**: nenhum `@GetMapping` de listagem encontrado sem `Pageable` (varredura em todos os `**/controller/*.java`); os únicos `@GetMapping` sem `Pageable` são detalhe por id, ações de estado (`/config`, `/resumo`, `/{id}/status`) e os relatórios PDF (que não são listagem paginável por natureza — tratados no achado 1).
- **Parâmetros de janela do dashboard/financeiro**: `vendasMensais`/`consumoFilamentoMensal`/`FinancialTransactionController` (`resumo/mensal`) e `topClientes` (limite) já usam `Math.clamp` para limitar `meses` (1–60) e `limite` (1–50) — não rejeitam, ajustam, como documentado no `PROJECT_CONTEXT.md`; único ponto sem janela é o achado 2.
- **Frontend — cache/staleTime**: `QueryClient` global (`frontend/src/main.tsx:12-20`) usa `staleTime: 30_000` e `refetchOnWindowFocus: false` — razoável para o volume do sistema; `ProducaoAndamento.tsx` usa `refetchInterval: 60_000` com `size: 5`, não é excessivo; nenhum outro `refetchInterval`/polling agressivo encontrado no restante do frontend.
- **Frontend — bundle/virtualização**: tabelas usam `TablePagination` server-side (não renderizam listas grandes de uma vez) em todos os módulos CRUD auditados; nenhum import de biblioteca pesada fora do já documentado (MUI, Recharts, React Hook Form/Zod) encontrado nos arquivos revisados.
- **Queries nativas de agregação (dashboard/financeiro/relatório) já cobertas por índice** (fora do achado 2): `DashboardQueryRepository.pedidosPorMes`/`faturamentoPorMes`/`consumoFilamentoPorMes`, `FinancialQueryRepository.totaisPorTipoEStatus`/`movimentoPagoPorMes`, `ReportQueryRepository.pedidosDoPeriodo`/`transacoesDoPeriodo`/`consumoPorFilamento` — todas usam `WHERE` sobre colunas de data com janela limitada (exceto `topClientes`, achado 2); os índices ausentes que apoiariam essas colunas de filtro já estão no `database-audit.md` (A1/A2/M2).
