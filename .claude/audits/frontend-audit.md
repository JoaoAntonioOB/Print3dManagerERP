### Achados por severidade

**ALTO**
1. **Regressão do gotcha Jackson `non_null` em Estoque de insumos** — `frontend/src/pages/inventory/InventoryPage.tsx:228` usa `item.custoUnitario !== null ? moeda.format(item.custoUnitario) : '—'`. `custoUnitario` é opcional no backend (`InventoryItemCreateRequest`/`InventoryItemUpdateRequest` só têm `@Positive`, sem `@NotNull`), então quando não informado o Jackson (`default-property-inclusion: non_null`) omite o campo do JSON e ele chega como `undefined` no frontend, não `null`. Com a comparação estrita `!== null`, `undefined !== null` é `true`, e o código tenta `moeda.format(undefined)`, exibindo **"R$ NaN"** na coluna "Custo" em vez de "—". Reproduzir: cadastrar um item de estoque sem preencher "Custo unitário (R$)" (campo é opcional no `InventoryFormDialog`, sem asterisco) e olhar a linha na tabela de `/estoque`. Esse exato gotcha já foi documentado como corrigido em Orçamentos (`PROJECT_CONTEXT.md`, Parte 7) — `QuoteFormDialog.tsx` e `PrintsPage.tsx` (`impressao.custoTotal != null`) usam a comparação correta (`!= null`), mas `InventoryPage.tsx` reintroduz o bug. Correção sugerida: trocar `!== null` por `!= null` na linha 228 (mesmo padrão de `PrintsPage.tsx:209`).

**MÉDIO**
2. **Mesmo padrão frágil em Filamentos, porém de menor probabilidade de disparo** — `frontend/src/pages/filaments/FilamentsPage.tsx:254` tem a mesma comparação `filamento.custoPorKg !== null ? moeda.format(...) : '—'`. Diferente do Estoque, `custoPorKg` é `@NotNull` tanto no create quanto no update do backend (`FilamentCreateRequest`/`FilamentUpdateRequest`), então hoje não deveria chegar `undefined` via fluxo normal da API — mas o tipo TS (`custoPorKg: number | null`) e o código continuam "mentindo" sobre a possibilidade real de omissão (registros legados/seed anteriores à validação, ou se a obrigatoriedade for relaxada no futuro, voltam a quebrar silenciosamente com "R$ NaN"). Sugestão: alinhar com o padrão `!= null` por defesa e consistência com o resto do código, já que o campo é tipado como nullable no client.
3. **`CartaoAcao` (dashboard) não é acessível por teclado/leitor de tela** — `frontend/src/pages/dashboard/AcoesHoje.tsx:23-35` usa um `<Paper onClick={...}>` como item clicável navegável (cards "pedidos aguardando produção" / "impressões em andamento" / "itens com estoque baixo"). É o único lugar do código onde um elemento clicável não é `Button`/`IconButton`/`ListItemButton` (todo o resto do app usa componentes MUI focáveis nativamente, conforme confirmado por grep). Sem `role="button"`, `tabIndex={0}` e `onKeyDown` (Enter/Space), o card não recebe foco por Tab nem é ativável por teclado, e leitores de tela não o anunciam como interativo. Sugestão: trocar `Paper` por `ButtonBase` (ou envolver em `CardActionArea`) mantendo o mesmo visual via `sx`.

**BAIXO**
4. **Validação de campo obrigatório condicional só via toast, sem estado de erro no campo** — dois casos: `frontend/src/pages/users/UserFormDialog.tsx:93-97` (senha obrigatória só no cadastro) e `frontend/src/pages/prints/PrintFinishDialog.tsx:105-108` (motivo da falha obrigatório só no modo "falhar"). Nos dois, a checagem ocorre no handler `enviar` com `toast.error(...)` e `return`, sem popular `errors.senha`/`errors.motivoFalha` do RHF — o campo não fica vermelho nem ganha `helperText` de erro, só o toast avisa. É um padrão consistente entre os dois (não é acidental), mas diverge da UX dos demais campos obrigatórios da mesma tela, que mostram erro inline. Não é um bug funcional (o submit é bloqueado corretamente), só uma pequena inconsistência de affordance visual.
5. **Navegação de atalho "estoque baixo" sempre aponta para `/filamentos`, mesmo quando o alerta é só de insumos** — `frontend/src/layout/NotificacoesMenu.tsx:49`, `frontend/src/pages/dashboard/AcoesHoje.tsx:99` e `EstoqueCritico.tsx:90` (botão "Ir para estoque") levam o usuário para `/filamentos` independente de o item crítico ser filamento ou item de `/estoque` (dois módulos distintos no menu). Não é um erro de dado, só uma pequena imprecisão de navegação quando o alerta é 100% de insumos gerais.

Não é erro, é característica de app SPA sem code-splitting por rota. Fora do escopo profundo desta auditoria (é `performance`), mas fica registrado porque apareceu no build.
